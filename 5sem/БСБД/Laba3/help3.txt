Как RLS блокирует кросс-сегментные операции:

Для SELECT - политики автоматически добавляют условие WHERE segment_id = текущий_сегмент
Для INSERT - WITH CHECK проверяет, что новый segment_id = текущему сегменту
Для UPDATE - USING проверяет старые записи, WITH CHECK - новые значения
Для DELETE - USING гарантирует удаление только своих записей

1. Какая ось изоляции выбрана и почему?
Ответ: Географические филиалы студии дубляжа. Это соответствует бизнес-логике - каждый филиал работает независимо.

2. Почему использован FORCE RLS?
Ответ: Чтобы политики применялись ко всем пользователям, включая владельца таблицы и администраторов, предотвращая обход безопасности.

3. Как работает функция set_session_ctx?
Ответ: Это SECURITY DEFINER функция, которая проверяет права роли на сегмент через segment_role_acl, затем устанавливает GUC-параметры сессии.

4. Чем отличается USING от WITH CHECK в политиках?
Ответ: USING фильтрует существующие записи, WITH CHECK валидирует новые данные при INSERT/UPDATE.

5. Как аудитор обходит RLS ограничения?
Ответ: Через условие current_user = 'auditor' в политиках, которое возвращает TRUE и отключает фильтрацию по сегментам.

6. Какие индексы созданы и зачем?
Ответ: Составные индексы вида (segment_id + поле) для оптимизации запросов с фильтрацией по сегментам.

7. Как обеспечивается ссылочная целостность?
Ответ: Через FOREIGN KEY constraints от segment_id в таблицах app.* к ref.segments.

8. Что такое кросс-сегментные операции?
Ответ: Любые действия с данными другого сегмента - чтение, запись, изменение, удаление.

9. Как тестировалась изоляция данных?
Ответ: Проверялось, что пользователи не видят чужие данные, не могут вставлять/обновлять с чужими segment_id.

10. Почему функция set_session_ctx - SECURITY DEFINER?
Ответ: Чтобы она выполнялась с правами владельца, но контролировала доступ на основе segment_role_acl.

11. Как обрабатывается случай, когда пользователь не установил контекст?
Ответ: Функция segment_is_visible генерирует исключение с требованием вызвать set_session_ctx.

12. Может ли аудитор изменять данные?
Ответ: Нет, у аудитора только права на SELECT, политики на модификацию остаются строгими.

13. Как работает фильтрация для voice_actor?
Ответ: Двойная проверка - по segment_id и actor_id, чтобы актёр видел только свои контракты.

14. Почему в индексах segment_id на первом месте?
Ответ: Чтобы сначала отфильтровать по сегменту, а затем по другим полям - это оптимально для RLS.

15. Что происходит при попытке вставить запись с несуществующим segment_id?
Ответ: FOREIGN KEY constraint блокирует операцию, так как segment_id должен существовать в ref.segments.

1. Чем отличается ENABLE ROW LEVEL SECURITY от FORCE ROW LEVEL SECURITY?
Ответ: ENABLE RLS включает механизм, но владелец таблицы может обходить политики. FORCE RLS применяет политики ко всем пользователям без исключений.

2. Почему в вашем проекте использован именно FORCE RLS?
Ответ: Чтобы гарантировать, что даже владелец таблицы и администраторы не смогут обойти политики безопасности и получить доступ к чужим сегментам.

3. Какие типы политик RLS вы создавали?
Ответ: CREATE POLICY для SELECT, INSERT, UPDATE, DELETE с отдельными условиями для каждой операции.

4. Как RLS взаимодействует с обычными правами доступа PostgreSQL?
Ответ: RLS работает поверх стандартных привилегий. Сначала проверяются права на таблицу, затем применяются RLS политики.

5. Может ли пользователь с правами SUPERUSER обойти FORCE RLS?
Ответ: Нет, FORCE RLS блокирует доступ даже для SUPERUSER, если только он явно не отключит RLS для сессии.

6. Как происходит фильтрация при JOIN запросах с RLS?
Ответ: RLS политики применяются к каждой таблице в запросе отдельно, обеспечивая изоляцию на уровне отдельных таблиц.

7. Что будет если в политике не указать WITH CHECK для INSERT?
Ответ: Пользователь сможет вставлять записи с любыми segment_id, что нарушит изоляцию. WITH CHECK обязателен для защиты от кросс-сегментных вставок.

8. Почему вы использовали отдельные политики для SELECT, INSERT, UPDATE?
Ответ: Чтобы гибко настраивать правила для разных операций - например, давать аудитору только SELECT, но не разрешать модификацию данных.

9. Как RLS влияет на производительность?
Ответ: Добавляет дополнительное условие WHERE к каждому запросу, но с правильно созданными индексами влияние минимально.

10. Можно ли временно отключить RLS для конкретной операции?
Ответ: Да, владелец таблицы может выполнить SET row_level_security = off, но при FORCE RLS это не сработает для обычных пользователей.


Контекст в вашей БД - это текущий сегмент (филиал) и актёр, с которыми работает пользователь.

Передача контекста - процесс установки этих параметров через функцию set_session_ctx(), чтобы RLS политики знали, к каким данным предоставлять доступ.

Проще: Контекст = "Я сейчас работаю с филиалом Москва, актёр ID 1". RLS использует эту информацию чтобы показывать только соответствующие данные.

Функция set_session_ctx делает:

Проверяет права - может ли текущая роль работать с запрашиваемым сегментом
Проверяет актёра - принадлежит ли указанный актёр к этому сегменту (для voice_actor)
Устанавливает настройки - запоминает segment_id и actor_id для текущей сессии
Автоматически сбрасывается - после завершения транзакции контекст очищается
Итог: Безопасно "включает" нужный филиал для работы пользователя.
