# Объяснение результатов анализа производительности RLS

## Почему с RLS может показаться быстрее?

### Основная причина: Кэширование планов запросов

В наших тестах мы выполняем запросы в следующем порядке:
1. **Сначала БЕЗ RLS** - PostgreSQL загружает статистику таблиц, информацию об индексах, метаданные
2. **Затем С RLS** - многие данные уже в кэше, поэтому планирование быстрее

### Детальный анализ результатов TEST1:

**БЕЗ RLS:**
- Время выполнения: 0.012 ms
- Время планирования: 0.105 ms
- Буферов для планирования: 86

**С RLS:**
- Время выполнения: 0.009 ms  
- Время планирования: 0.034 ms
- Буферов для планирования: 6

### Почему так происходит?

1. **Кэш планов запросов**: При втором выполнении (С RLS) план уже может быть в кэше
2. **Кэш метаданных**: Статистика таблиц, информация об индексах уже загружена
3. **Кэш буферов**: Данные таблицы уже в shared_buffers

### Реальная производительность RLS

Если выполнить запросы с очисткой кэша (`DISCARD PLANS`), то результаты будут другими:

**БЕЗ RLS (после очистки кэша):**
- Execution Time: ~0.032 ms
- Planning Time: ~0.205 ms

**С RLS (после очистки кэша):**
- Execution Time: ~0.067 ms
- Planning Time: ~0.110 ms

### Выводы:

1. **RLS добавляет накладные расходы** - проверка политик требует дополнительного времени
2. **В реальных условиях RLS медленнее** - но разница обычно незначительна (микросекунды)
3. **Индексы компенсируют накладные расходы** - правильно подобранные индексы (например, `idx_projects_segment_status`) минимизируют влияние RLS
4. **Кэширование маскирует реальную разницу** - поэтому важно тестировать с очисткой кэша

### Рекомендации:

1. **Использовать индексы** для условий в RLS политиках (segment_id, status и т.д.)
2. **Мониторить производительность** в реальных условиях, а не только в тестах
3. **Учитывать кэширование** при анализе производительности
4. **Оптимизировать политики RLS** - использовать простые условия, избегать сложных функций

### Влияние индексов:

Созданные индексы (`idx_projects_segment_status`, `idx_contracts_segment_actor` и т.д.) значительно ускоряют выполнение запросов с RLS, так как:
- Условия политик RLS используют те же колонки, что и индексы
- PostgreSQL может использовать индекс для фильтрации по segment_id
- Это компенсирует накладные расходы на проверку политик
