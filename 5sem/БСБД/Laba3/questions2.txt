
ПУНКТ 1: SECURITY DEFINER-функции

1. Что такое SECURITY DEFINER-функция?
Ответ: Функция, которая выполняется с правами владельца функции, а не вызывающего пользователя.
Позволяет дать ограниченным ролям доступ к привилегированным операциям.

3. Зачем нужен search_path в SECURITY DEFINER-функциях?
Ответ: Для защиты от атак через подмену схем. Устанавливается явно: SET search_path = app, ref, audit, public

4. Какие валидации есть в функции create_contract?
Ответ: Проверка существования проекта и актёра, уникальность номера контракта, положительность суммы, корректность дат (end_date >= signed_date)

ПУНКТ 3: CHECK vs триггер

12. Какое бизнес-правило выбрано для сравнения?
Ответ: end_date >= signed_date и для завершённых контрактов end_date <= CURRENT_DATE

13. В каких файлах реализовано сравнение?
Ответ: lr2_03_check_vs_trigger.sql (создание таблиц) и lr2_06_performance_test.sql (тест производительности)



16. В чём разница между CHECK и триггером?
Ответ: CHECK - встроенное ограничение на уровне БД, интегрируется в план запроса. 
Триггер - отдельная функция, требует переключения контекста.

17. Когда использовать CHECK, а когда триггер?
Ответ: CHECK - для простых правил (сравнения, проверки значений).
Триггер - для сложной логики, логирования, обращения к другим таблицам.

При падении БД CHECK надежнее - правила целостности встроены в саму таблицу и восстановятся автоматически. 
Триггеры сложнее - их логику нужно перезапускать, возможны рассинхронизации и потеря данных при сбое.
CHECK проще для восстановления.

21. Как логируются вызовы функций?
Ответ: Через функцию audit.log_function_call(), которая вызывается внутри каждой SECURITY DEFINER-функции

23. Что логируется при успешном вызове?
Ответ: Входные параметры, возвращаемое значение, время выполнения, успешность (success = true)

24. Что логируется при ошибке?
Ответ: Входные параметры, сообщение об ошибке, время выполнения, успешность (success = false)

ДОПОЛНИТЕЛЬНЫЕ ВОПРОСЫ

31. Что такое CHECK и триггер - реализация?
Ответ: CHECK - встроенное ограничение на уровне таблицы, проверяет условие при INSERT/UPDATE. 
Триггер - функция, выполняемая автоматически до/после операции. 

32. Какие чувствительные данные и операции есть в БД?
Ответ: Чувствительные данные: passport_data, tax_id (Restricted), salary_amount, bank_details, budget (Confidential), client_contacts (Internal). Чувствительные операции: создание контрактов, обновление зарплат, регистрация сессий записи - реализованы через SECURITY DEFINER-функции.

33. Что такое pgTAP?
Ответ: pgTAP - фреймворк для тестирования PostgreSQL, позволяет писать unit-тесты на SQL. В ЛР2 тесты реализованы через psql-скрипты (lr2_04_tests.sql), но можно использовать pgTAP для более структурированного тестирования.

34. Как модифицировали функции под логирование вызовов?
Ответ: В начале функции фиксируется время старта, формируется JSON с входными параметрами. 
После выполнения вызывается audit.log_function_call() с параметрами, возвращаемым значением и временем выполнения. В блоке EXCEPTION логируется ошибка с сообщением.

35. Что такое RLS (Row Level Security)?
Ответ: RLS - механизм безопасности PostgreSQL, ограничивающий доступ к строкам таблицы на основе политик. В БД включён для таблиц actors, contracts, projects, recording_sessions. Актёры видят только свои данные, менеджеры - проекты своей студии.

36. Что такое DEFAULT PRIVILEGES?
Ответ: DEFAULT PRIVILEGES - автоматическое назначение привилегий для объектов, создаваемых в будущем. В script6.sql настроены DEFAULT PRIVILEGES для ролей app_reader, app_writer, auditor, чтобы новые таблицы автоматически получали нужные права без ручного GRANT.

37. Что такое DDL и DML?
Ответ: DDL (Data Definition Language) - команды определения структуры: CREATE, ALTER, DROP таблиц, функций, ролей. 
DML (Data Manipulation Language) - команды работы с данными: SELECT, INSERT, UPDATE, DELETE. В ЛР2 проверяется, что обычные роли не могут выполнять DDL, а DML в audit запрещён.

RLS
Каждый сотрудник видит только свои задачи
Пользователь видит только данные своего региона
Студент видит только свои оценки

CHECK — защита на входе. Не дает записать плохие данные. Проще и надежнее.

Триггер — реакция на действие. Может изменять данные или делать сложные проверки, но сложнее и уязвим для ошибок.

Безопасность: CHECK надежнее, так как его невозможно обойти, а в триггере можно допустить ошибку логики.



CHECK всегда выполняет оба условия:
end_date IS NULL OR end_date >= signed_date
status != 'completed' OR (end_date IS NOT NULL AND end_date <= CURRENT_DATE)
Всегда оцениваются оба выражения.

Триггер использует условную логику:
Проверка дат выполняется только если end_date IS NOT NULL
Проверка для completed выполняется только если status = 'completed'
