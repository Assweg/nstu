38. Какие индексы используются, виды?
Ответ: Используются B-tree индексы (по умолчанию в PostgreSQL). Виды: обычные индексы (idx_contracts_project_id, idx_contracts_actor_id), частичные индексы (idx_actors_active WHERE is_active = true), индексы на внешние ключи, индексы для аудита (idx_login_log_time, idx_function_calls_time). Всего создано более 10 индексов для оптимизации запросов.

39. Какие чувствительные данные есть в БД?
Ответ: Restricted: passport_data, tax_id (паспортные данные, ИНН). 
Confidential: salary_amount, bank_details, budget, terms (зарплаты, банковские реквизиты, бюджеты). 
Internal: client_contacts (контакты клиентов). 
Public: общая информация о проектах, названия фильмов.

40. На примере моей БД - что реализовано?
Ответ: БД студии дубляжа с 4 схемами (app, ref, audit, stg), RLS политиками, аудитом подключений и DML операций, SECURITY DEFINER-функциями для чувствительных операций, журналом вызовов функций, классификацией данных по уровням конфиденциальности, ролевой моделью с разделением прав.

41. SECURITY DEFINER-функция?
Ответ: Функция, выполняющаяся с правами владельца, а не вызывающего пользователя. Позволяет ограниченным ролям выполнять привилегированные операции. В ЛР2 реализованы 3 функции: create_contract, update_contract_salary, register_recording_session.

42. Зачем нужен search_path?
Ответ: Определяет порядок поиска объектов (схем) в БД. В SECURITY DEFINER-функциях устанавливается явно (SET search_path = app, ref, audit, public) для защиты от атак через подмену схем. Без этого злоумышленник может создать объект в схеме public и перехватить выполнение функции.

43. Что такое сегментация и с точки зрения безопасности?
Ответ: Сегментация - разделение данных на логические части (схемы, таблицы).
С точки зрения безопасности: изоляция данных по уровням доступа (app - бизнес-данные, audit - логи, ref - справочники), применение разных политик безопасности к разным сегментам, ограничение доступа через схемы и RLS.

44. Зачем разделять БД на схемы?
Ответ: Изоляция данных по назначению (app - бизнес, audit - аудит, ref - справочники, stg - временные), разделение прав доступа (разные роли для разных схем), организация кода, безопасность (ограничение видимости объектов), упрощение управления привилегиями через DEFAULT PRIVILEGES.

45. Как реализуется аудит подключений пользователей?
Ответ: Таблица audit.login_log, функция audit.log_connection() (SECURITY DEFINER), автоматическое логирование через pgaudit и ручное через функцию log_session_start(). Логируется: username, client_ip, время подключения, успешность, причина ошибки. Доступ к логам только у роли auditor.

46. Виды данных и как они реализуются и кто их может видеть?
Ответ: Public - общая информация (видят все).
Internal - контакты клиентов (видят app_writer, app_owner).
Confidential - зарплаты, бюджеты, банковские реквизиты (видят app_owner, dml_admin, через SECURITY DEFINER-функции).
Restricted - паспортные данные, ИНН (видят только app_owner, security_admin). Реализуется через RLS политики, роли, SECURITY DEFINER-функции и маскирование данных.
